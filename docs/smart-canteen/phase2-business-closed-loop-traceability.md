# 阶段 2：统一食谱与采购核心闭环追踪

## 目标

将 `PUBLISHED daily_menus` 作为采购需求的唯一业务输入，形成：

```text
已发布食谱 -> 配方需求快照 -> 采购计划草稿 -> 人工调整/确认
         -> 采购订单 -> 供应商确认 -> 部分/完整验收
         -> 入库批次 + 库存 + 溯源码
```

## 设计决策

- 采购计划只消费运营模块的 `daily_menus`、`daily_menu_items`、`dishes` 和 `dish_ingredients`，不再把旧的单菜单配方接口当作新闭环的事实来源。
- 采购计划保存计算时的需求、库存和未入库订单快照；之后食谱或库存变化不会静默改写已经生成的计划。
- 订单明细保留采购业务单位，另存累计验收基础量；验收和库存批次统一保存基础单位。
- 旧 `/api/v1/procurement-plans/generate` 和 `/api/v1/inventory/receipts` 作为兼容适配器保留，不与新计划表混用。

## 验收切片

| 切片 | 结果 | 验收证据 |
| --- | --- | --- |
| P2-S1 | 已发布食谱按份数聚合基础单位需求，扣库存和未入库订单 | `ProcurementPlanService` 模块测试、HTTP 生成测试 |
| P2-S2 | 计划持久化、幂等、人工调整、版本保护和状态机 | 计划生命周期模块/HTTP 测试 |
| P2-S3 | CONFIRMED 计划转订单并保留关联 | 转单 HTTP 测试、订单幂等测试 |
| P2-S4 | 确认订单部分/完整验收，批次、库存、溯源同事务 | 验收 HTTP 测试、重试和超量测试 |
| P2-S5 | OpenAPI、前端 API、构建和全量验证同步 | contract test、Maven、npm test/build |

## 不在本阶段完成

供应商门户、票证 OCR、自动出库/FIFO、结算成本、采购统计以及外部平台/设备接入属于后续阶段；它们使用本阶段形成的计划、订单、验收、批次和溯源事实，不另建平行采购库存事实。
