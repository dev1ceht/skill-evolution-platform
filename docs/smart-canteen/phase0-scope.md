# 阶段 0：范围与架构基线

状态：已完成

日期：2026-08-14

## 目标

阶段 0 不实现业务代码，先把两份设计文档收敛为可执行的产品和工程基线。阶段 1 以后所有数据库、接口、页面和测试任务都必须引用本阶段的需求 ID、领域词汇和状态模型。

## 版本边界

### MVP：单校单食堂真实运营

- 学校、食堂、人员、供应商和账号权限。
- 食材、营养、菜品、配方和带量日食谱。
- 食谱审批、公示和版本不可变。
- 采购计划、采购订单、验收、入库、批次库存和出库。
- 台账类型、频次、记录、照片和周期预警。
- 证照/健康证基础档案和临期预警。
- 通知公告、食堂风采、停餐报备和投诉建议的最小审核/发布流程。
- 采购结算、收支记录和成本核算基础流程。
- 微信小程序最小访问：扫码登录、查看食谱、记录台账（真实微信凭据属于联调前置条件）。
- 溯源码查询、学校端首页和基础统计。

### V1：教育局与市级监管

- 多学校/多食堂区域数据权限。
- 采购、库存、台账、风险和规范化评分。
- 市级数据上报、同步、质量校验和T+1汇总。
- 大屏统计、价格监管、整改任务和效果跟踪。

### V2：二期设备与评价扩展

- 明厨亮灶、第三方单点登录、晨检仪、高拍仪、电子秤和标签打印机。
- 食堂百科、批量导入、满意度调查和供应商评价。
- 微信小程序高级能力、短信/微信通知和真实厂商联调。

## 设计冲突处理

| 冲突 | 阶段 0 决定 |
| --- | --- |
| 概要设计将硬件采购/集成列为非范围，二期设计要求设备接入 | 设备能力归入 V2；MVP 只定义设备适配边界，不阻塞核心业务开发 |
| 账号密码登录与微信小程序登录并列 | MVP 同时完成账号登录/RBAC 和微信小程序扫码登录、食谱查看、台账记录；真实微信凭据和生产联调作为外部前置条件 |
| 旧菜单审批模型和新日食谱模型并存 | 以带审批状态的日食谱作为唯一后续写模型，旧模型只兼容读取/迁移 |
| 概要接口与二期接口命名不完全一致 | 后续统一采用 `/api/v1` 规范资源路径，二期厂商路径仅作为兼容适配路由 |
| 预警中心既接收外部警情又产生内部预警 | 领域统一为 Alert；内部规则和外部适配器都生成同一类归一化预警 |

## 不能开始对应联调的前置条件

- 运营范围必须明确是单食堂、单学校还是监管区域。
- 供应商、设备、短信、对象存储和区县平台的真实接口合同必须分别确认。
- 订单状态、验收责任人和库存扣减规则必须由业务负责人确认。
- 食谱营养标准和食材内置库来源必须确定。

以上条件不会阻塞阶段 1 的基础主数据、权限和核心领域建模，但会阻塞对应的真实设备、第三方平台、营养计算和生产通知联调。
