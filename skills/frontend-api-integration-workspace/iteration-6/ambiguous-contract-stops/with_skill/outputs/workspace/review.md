# Contract review

审查范围：`GET /api/v1/menus`。

## operationId

缺失证据：该操作没有声明 `operationId`。契约中也没有其他可作为稳定操作标识的明确约定。

风险：前端请求层、类型生成、缓存键和测试无法依据契约获得稳定且可追踪的操作名称；若按路径或方法自行命名，可能与后端或团队约定不一致。

需要用户确认：请确认该操作应使用什么唯一的 `operationId`，以及命名是否需要遵循现有项目或 API 的命名规范。

## success schema

缺失证据：`200` 响应声明了 `application/json`，但 `content` 下没有 `schema`，因此无法确认返回值是数组、对象、信封结构，还是其他 JSON 值，也无法确认菜单项字段。

风险：客户端无法安全生成响应类型或判断空结果；错误的结构假设可能导致运行时解析失败、页面渲染错误或丢失业务字段。

需要用户确认：请提供 `200` 响应的完整 `schema`（包括菜单项字段、必填性和数组/对象关系），或提供一份经确认的实际响应示例及其稳定性说明。

## authentication

缺失证据：契约没有定义 `components.securitySchemes`，也没有在根级或该操作级声明 `security`。现有内容不足以判断该接口是否公开，或需要哪种认证方式、凭据位置和权限范围。

风险：客户端可能遗漏必需的认证信息，导致请求被拒绝；也可能错误地发送凭据，造成安全或权限问题。

需要用户确认：请确认该接口是否需要认证；若需要，请明确认证方案、凭据传递位置、所需权限/作用域，以及认证声明应作用于全局还是仅此操作。

## pagination

缺失证据：请求没有声明 `page`、`offset`、`cursor` 或其他分页参数；成功响应也没有 schema，因而没有元数据或下一页游标的证据。无法确定接口是分页、一次返回全部数据，还是使用未在契约中描述的分页机制。

风险：前端可能一次请求过量数据、遗漏结果或重复/跳过结果；在未确认模式的情况下实现分页还可能使用错误的参数名、边界语义或响应字段。

需要用户确认：请确认该接口是否分页。若分页，请明确分页模式（page、offset、cursor 或其他）、请求参数名称及默认/边界规则、响应中的列表和总数/下一页字段，以及排序稳定性；若不分页，请明确返回完整结果集的约束和数据量上限。
