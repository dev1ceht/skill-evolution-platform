# Smart Canteen Secure Integration

先证明信任边界和权限模型，再实现连接器。将 HTTP 输入、设备/厂商响应、消息、文件、模型输出和后续反馈全部视为不可信数据。

## Workflow

1. 识别变更涉及的资产、操作者、数据分类和信任边界。处理外部平台、设备或异步基础设施时，先读 `references/trust-boundaries.md`。
2. 为每个入口写正常用例和至少一个滥用用例：越权跨食堂、重复上报、重放、篡改、超大输入、敏感信息泄露、服务不可用或乱序消息。
3. 定义身份与授权：谁发起、凭据由谁管理、允许访问哪些 `schoolId + canteenId`、服务端在哪里强制校验。客户端传入的范围不能单独作为授权依据。
4. 定义输入契约和规范化边界。厂商 wire model 只存在于 adapter；领域层只接收校验后的规范化对象。为未知枚举、时区、单位、分页和错误码设置显式失败策略。
5. 定义重复与故障语义：幂等键、去重窗口、超时、有限重试、退避、断路、顺序、死信和人工补偿。不可安全重试的写操作默认不自动重试。
6. 定义秘密和日志策略：凭据只从受控环境注入；日志、fixture、OpenAPI、verification 和 Skill 不得包含密码、token、手机号等敏感值。
7. 以最小权限实现 adapter。限制网络目标、重定向、输入大小和响应大小；数据库查询参数化；文件路径必须限制在配置根目录内。
8. 添加授权、跨租户、重放、幂等、冲突、超时和降级测试。只有可复现的攻击路径才报告为漏洞；其余记录为 hardening 建议。
9. 输出残余风险、依赖的外部控制、凭据/网络前提和上线门禁。

## Mandatory boundaries

- 核心查询与写入必须在服务端执行学校/食堂范围校验。
- 同一外部来源的事件必须使用来源身份与厂商事件 ID 建立唯一性；同键异载荷要拒绝并审计。
- 模型生成的 candidate 只能进入 staged 状态，不能直接写生产 Skill 或执行生成的命令。
- 未获得真实接口合同、网络策略和凭据时，只能交付端口、模拟器或契约测试，不能声称真实集成。
- Redis/RabbitMQ 不得只是容器占位；没有消费、失效或恢复语义时保持未接入状态。

## Output contract

产出简洁威胁模型、信任边界与数据流、控制措施、滥用测试、残余风险和明确的上线阻断项。安全结论必须指向代码、配置或测试证据。
