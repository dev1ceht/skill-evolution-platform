# Smart Canteen Domain Modeling

让业务概念决定模块边界，不让 HTTP 字段或数据库表结构反向定义领域。优先建立稳定语言和不变量，再选择类、表和接口。

## Workflow

1. 收集本次范围内的需求陈述、设计文档术语、代码类型、表名、OpenAPI 字段和测试名称。发现同词异义或一义多词时显式列出。
2. 读取 `references/domain-map.md`，确认现有上下文和跨模块关系。新增概念时说明它属于哪个上下文以及不属于哪里。
3. 建立术语表：业务名称、精确定义、标识、生命周期、允许操作者、学校/食堂范围和禁止使用的歧义别名。
4. 识别聚合与不变量。只把必须在同一事务内保持一致的对象放入一个聚合；跨聚合规则通过应用服务、领域服务或事件协调。
5. 为写流程画出命令、前置条件、状态迁移、结果、幂等和并发冲突；为查询定义范围、分页和一致性需求。
6. 定义公开模块接口和端口。厂商模型、HTTP envelope、JDBC row、Redis value 和消息 payload 都留在 adapter 边界。
7. 用代表性场景和反例验证模型：跨食堂访问、重复审批/入库/上报、单位换算、周期结束、同键异载荷和外部系统失败。
8. 非显然的边界或取舍写入简短 ADR，记录上下文、决定、替代方案和后果；不要只记录最终类图。
9. 将确认后的术语、不变量和接口同步到 requirements、OpenAPI、迁移与测试，检查命名漂移。

## Modeling rules

- `schoolId + canteenId` 是核心业务数据的范围身份，不是可选展示字段。
- 菜单审批、采购计算、库存入库、台账完成和预警处置各自拥有明确状态与幂等语义。
- 历史工作流门面不得回流为运行时兼容层；规则应归属于当前 canonical 应用服务和聚合。
- 外部平台通过 anti-corruption adapter 规范化后进入领域；不要让厂商枚举和字段渗入核心模型。
- 只有真实的跨模块一致性需求才能扩大事务边界。

## Output contract

输出术语表、上下文/模块边界、聚合与标识、不变量、状态迁移、公开接口、端口、代表性测试场景和必要 ADR。未解决的术语冲突必须单列。
